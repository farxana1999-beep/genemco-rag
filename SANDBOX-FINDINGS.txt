--------------------------------------------------------------------
1. SCHEMA
--------------------------------------------------------------------

All eight expected fields are present in all 50 records:
question, answer, raw_model_code, clean_model_code, source_page,
specs, requires_numeric_gate, token_count.

Two extra fields are also present: equipment_category and
safety_warnings.

However, three fields are the wrong SHAPE for our pipeline:

  specs
     Harvest supplies a flat dictionary of strings, for example
     {"Max RPM": "7000 RPM"}.
     Our pipeline expects each spec to carry value, unit, source,
     source_ref, method and confidence.
     Result: these specs arrive with NO PROVENANCE AT ALL.

  source_page
     Harvest supplies a URL string.
     Our FAQItem expects an integer page number (Optional[int]).
     Result: type mismatch, fails validation outright.

  spec_field and value
     Required by our FAQItem. Not present in the harvest at all.

Field naming is also misleading:

  raw_model_code    is not a model code. It is the full product
                    title, e.g. "Frick XJB151 Rotary Bare Screw
                    Compressor".

  clean_model_code  is that same title lowercased with all
                    punctuation stripped, e.g.
                    "frickxjb151rotarybarescrewcompressor".
                    It is a slug, not a code.


--------------------------------------------------------------------
2. SPEC INTEGRITY
--------------------------------------------------------------------

The specs themselves look genuine. They are nameplate-style entries:
Model, Serial No, Volume Ratio, Max RPM, Max Design Pressure,
Year Built, Refrigerant.

The ANSWERS are the problem. Every answer is an auto-generated
concatenation, and every question in the sample is the identical
template "What are the specifications for X?".

Example, record 0:

  Q: What are the specifications for Frick XJB151 Rotary Bare Screw
     Compressor?
  A: Specifications for Frick XJB151 Rotary Bare Screw Compressor:
     SKU: TPC47 Brand: Frick Model: XJB151 Model: XJB151;
     Serial No: 0008J; Volume Ratio: 2.2-5.0; Max RPM: 7000 RPM;
     Max Design Pressure: 350 PSI; Year Built: 1998.

  attached specs:
     Model                = XJB151
     Serial No            = 0008J
     Volume Ratio         = 2.2-5.0
     Max RPM              = 7000 RPM
     Max Design Pressure  = 350 PSI
     Year Built           = 1998.

These are not really question-and-answer pairs. They are spec dumps
phrased as a question.

Visible data glitches:
  - One answer repeats "Model: XJB151 Model: XJB151".
  - Another states both "Model: TDSH233" and "Model: TDSH233S"
    within the same answer.
  - raw_model_code is not unique. Five of the first eight records
    share the title "Frick TDSH233S Rotary Bare Screw Compressor"
    with different SKUs and serial numbers.

NUMBERS NOT BACKED BY SPECS:
49 of the 50 records contain a number in the answer that does not
appear in that record's own specs.

The cause is systematic, not random. The answer embeds the SKU, for
example "SKU: TPC47", and our number extractor reads TPC47 as
containing the number 47. The SKU is not a spec, so it counts as
unverified. Record 0 flags 47, record 1 flags 46, record 2 flags 45.
It tracks the SKU every time.


--------------------------------------------------------------------
3. GATE ROUTING  (most important finding)
--------------------------------------------------------------------

requires_numeric_gate is set to true on all 50 records, but it is an
INERT BOOLEAN. Nothing in our codebase reads it. It is wired to
nothing.

More fundamentally, these records CANNOT ENTER THE GATE at all as
they stand. Attempting to build a FAQItem from a raw record fails:

  FAQItem.model_validate(record)  ->  ValidationError
     spec_field   Field required [type=missing]
     value        Field required [type=missing]

Our gate validates a specific CLAIM (a spec_field plus a declared
value) against verified specs. These records make no claim. They are
a blob of text. So the flag cannot route them "through" the gate,
because there is no path for them to travel.

To measure what would happen, a throwaway adapter was built:

  PASSED:    1 of 50
  REJECTED: 49 of 50   (all: "unverified numbers in answer")

Caution on reading that result: the 49 rejections are caused by the
SKU-digit artifact described in section 2, not by anything actually
being wrong with the specs. The gate is firing on a formatting quirk.
That number says very little about real data quality.


--------------------------------------------------------------------
4. MODEL-CODE PRECISION
--------------------------------------------------------------------

The concern about collapsing was justified.

clean_model_code strips every non-alphanumeric character:

  RXF-85-H   ->  rxf85h
  RXF-85H    ->  rxf85h      <-- INDISTINGUISHABLE

This is not theoretical. Scanning all 15,939 records:

  distinct clean_model_code values:            11,689
  clean codes that collapse 2+ distinct raws:     271

Real examples of collapsed pairs:
  "Ram Industries ... (500 HP, 460 Volt, 60 Hz)"
      and "... (500 Hp, 460 Volt, 60 Hz)"
  "Alfa Laval SS AlfaNova 76 ..."
      and "... AlfaNova76 ..."
  "Hansen H5601 ... (1/2 in x 1 in, 250 PSI)"
      and "... (1/2 in x 1 in. 250 PSI)"
      and "... (1/2 in. x 1 in. 250 PSI)"        (three into one)

GOOD NEWS: raw_model_code IS preserved verbatim, and it is genuinely
additional rather than a replacement. The XJF variant letters survive
there. Found in the file: 151A x1, 151L x2, 151M x2, 151N x3, for
example "Frick RXF-101-B Rotary Screw Compressor Package
(Frick XJF151N, 60 HP 575 V)".

So the variant distinction IS recoverable, but only if we ignore
clean_model_code for filtering, which appears to be the one job it
was built to do.

5. SOURCE TYPE
--------------------------------------------------------------------

Public storefront, definitively. Not Admin API.

No Admin-API-only markers appear anywhere in the sample. Checked for
and found absent: inventory_quantity, inventory_level, cost,
unpublished, published_at, variant_id, admin_graphql,
inventory_item_id.

All 50 source_page values are public product URLs of the form
https://www.genemco.com/products/...

For the client write-up: this data is the same provenance class as
our existing 20 SKUs. It should carry the same
sync_mode: "public_storefront" stamp and the same caveat that it is
not authoritative.

--------------------------------------------------------------------
RECOMMENDATION
--------------------------------------------------------------------

Do not ingest this as it stands. Cost is not the reason - it is
trivially cheap. Four things need deciding first:

1. requires_numeric_gate is decorative. It needs to be wired to
   something real, or removed. Shipping it as-is implies a safety
   property that does not actually exist.

2. clean_model_code is unsafe as a filter, with 271 confirmed
   collisions including the RXF-85-H / RXF-85H case. Filtering
   should use raw_model_code instead.

3. There is no provenance. Ingesting these would put unsourced specs
   into the same specs{} structure the FAQ engine reads, directly
   alongside our page-cited ones. That undercuts the guarantee the
   client report makes in its section 3.

4. The Q&A is templated. One question shape repeated 15,939 times
   will produce near-duplicate FAQs. That is both the generic output
   the SOW says to reject, and an SEO duplicate-content risk.

SAFEST PATH IF THE DATA IS WANTED:
Treat it as literature-style chunks for /search only - searchable,
but never feeding specs{} or the FAQ generator. This is the same
quarantine already used for safety text, and it sidesteps points
1, 3 and 4 entirely.
