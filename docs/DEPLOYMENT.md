# Deploying the Verified Query Service

How to run `api/query_app.py` behind Muiz's Worker. **Nothing here has been deployed.**
No host, URL or credential below is real: every value in `<ANGLE_BRACKETS>` must come
from Genemco or Muiz.

---

## 1. Target topology

```text
public client ──HTTPS──▶ Worker (198.199.121.125:8002)
                          owns: public exposure, JWT auth
                                   │
                                   │  private hop, X-Upstream-Token
                                   ▼
                          Verified Query Service  (api.query_app)
                          GET /health · POST /query
                          reads golden records from local disk
```

The service must accept traffic **only from the Worker**. Two controls, both recommended:

1. **Network** — bind to loopback or a private interface; never `0.0.0.0` on a public NIC.
2. **Shared secret** — set `QUERY_UPSTREAM_TOKEN`; the Worker sends it as `X-Upstream-Token`.
   `/health` stays open so the Worker can probe readiness.

The service needs **no** OpenAI, Pinecone or Docling credentials.

## 2. What was observed about the Worker

Checked on 14 Sep 2026 with two read-only requests:

| Request | Result |
|---|---|
| `GET http://198.199.121.125:8002/` | `200`, served by uvicorn |
| `GET http://198.199.121.125:8002/health` | `404 Not Found` |

The Worker is running. Its current upstream is reported to be `localhost:9000`, a
placeholder with nothing listening. `localhost` in a Worker config means *the Worker's
own machine*, which is why the options below differ by where the service runs.

## 3. Deployment options

### Option A — same machine as the Worker (least change)

| | |
|---|---|
| Service binds | `127.0.0.1:9000` |
| Worker upstream | `http://127.0.0.1:9000` — **matches the existing placeholder** |
| Publicly reachable? | No — loopback only |
| Worker config change | Add the `X-Upstream-Token` header only |

### Option B — separate host on a private network

| | |
|---|---|
| Service binds | `<PRIVATE_IP>:<PORT>` |
| Worker upstream | `http://<PRIVATE_IP>:<PORT>` |
| Firewall | allow `<PORT>` from the Worker's private IP only |
| Worker config change | new upstream URL + `X-Upstream-Token` header |

### Option C — managed platform

Possible, but the platform must offer private networking to the Worker, or the service
becomes publicly reachable and relies on the token alone. Not recommended without it.

## 4. What is needed to deploy — BLOCKED on these inputs

| # | Input | From | Why |
|---|---|---|---|
| 1 | Choice of option A, B or C | Genemco | Decides host, bind address and upstream URL |
| 2 | Host access: SSH hostname, username, and an agreed auth method | Genemco / Muiz | To install and run the service. Either authorise a deploy key, or run the commands below yourselves |
| 3 | Confirmation the Worker host is **persistent** | Muiz | The Sprint 1 handover said the harvest VM would be snapshotted and destroyed after standby; the service must not live on a machine scheduled for deletion |
| 4 | OS and Python version on the host (3.11+ needed) | Genemco / Muiz | Install path |
| 5 | Port confirmation (`9000` free for option A, or `<PORT>` for B) | Muiz | Avoid clashes |
| 6 | Who changes the Worker's upstream config | Muiz | The Worker is Muiz's code |
| 7 | How the Worker should pass `X-Upstream-Token` | Muiz | Header forwarding in the Worker |
| 8 | The token value — **generated by you, set directly on both machines, never sent in chat or email** | Genemco / Muiz | Shared secret |
| 9 | Process manager preference: systemd (default below) or Docker | Genemco / Muiz | Keeps the service running across reboots |
| 10 | Where service logs should go | Genemco / Muiz | Operations |
| 11 | How golden-record data reaches the host (scp, rsync, object storage) | Genemco / Muiz | ~100 MB of JSON, see §6 |

**Production upstream URL shape** once inputs 1–5 are known:

- Option A: `http://127.0.0.1:9000/query`
- Option B: `http://<PRIVATE_IP>:<PORT>/query`

## 5. Configuration

All configuration is environment variables. Nothing is hardcoded.

| Variable | Default | Purpose |
|---|---|---|
| `GENEMCO_API_HOST` | `127.0.0.1` | Bind address |
| `GENEMCO_API_PORT` | `9000` | Bind port |
| `QUERY_UPSTREAM_TOKEN` | *(unset)* | Shared secret; when set, `/query` requires `X-Upstream-Token` |
| `GENEMCO_GOLDEN_DIR` | `data/golden_records` | Authoritative golden records (`*.json`) |
| `GENEMCO_CATALOG_PATH` | `data/search_layer/catalog_golden_records.jsonl` | Catalog search layer |
| `GENEMCO_MANUAL_URLS` | `data/manual_urls.json` | Optional `{manual filename: url}` |
| `GENEMCO_FORWARDED_ALLOW_IPS` | `127.0.0.1` | Proxies trusted for `X-Forwarded-*` |
| `GENEMCO_API_DOCS` | `0` | `1` serves `/docs` and `/openapi.json` |
| `GENEMCO_LOG_LEVEL` | `info` | Log level |

## 6. Install and run (once access is granted)

```bash
# 1. Code and a Python environment
git clone <REPO_URL> genemco-rag && cd genemco-rag
python3 -m venv venv && . venv/bin/activate
pip install -r requirements-query.txt

# 2. Data — copied from the ingestion machine; not in git
#    data/golden_records/                         authoritative records
#    data/search_layer/catalog_golden_records.jsonl

# 3. Environment file, readable by the service user only
sudo install -m 600 /dev/null /etc/genemco-query.env
sudoedit /etc/genemco-query.env
#   GENEMCO_API_HOST=127.0.0.1
#   GENEMCO_API_PORT=9000
#   QUERY_UPSTREAM_TOKEN=<GENERATED_ON_THE_HOST>
#   GENEMCO_GOLDEN_DIR=/opt/genemco-rag/data/golden_records
#   GENEMCO_CATALOG_PATH=/opt/genemco-rag/data/search_layer/catalog_golden_records.jsonl

# 4. Smoke test in the foreground
set -a; . /etc/genemco-query.env; set +a
python -m api.query_app
```

Generate the token on the host rather than typing it anywhere else:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
```

### systemd unit (option A or B)

`/etc/systemd/system/genemco-query.service`:

```ini
[Unit]
Description=Genemco Verified Query Service
After=network-online.target
Wants=network-online.target

[Service]
User=<SERVICE_USER>
WorkingDirectory=/opt/genemco-rag
EnvironmentFile=/etc/genemco-query.env
ExecStart=/opt/genemco-rag/venv/bin/python -m api.query_app
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now genemco-query
sudo systemctl status genemco-query
```

## 7. Verification checklist

Run on the host after starting the service:

```bash
# 1. Ready — expect 200, "status": "ok", records > 0
curl -s http://127.0.0.1:9000/health

# 2. Token enforced — expect 401
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:9000/query \
  -H "Content-Type: application/json" -d '{"query":"oil charge","model_code":"RXF-85-H"}'

# 3. Verified answer — expect verified:true, source_page 7
curl -s -X POST http://127.0.0.1:9000/query \
  -H "Content-Type: application/json" -H "X-Upstream-Token: $QUERY_UPSTREAM_TOKEN" \
  -d '{"query":"oil charge","model_code":"RXF-85-H"}'

# 4. Not reachable from outside — run from another machine; expect a timeout or refusal
curl -s -m 5 http://<HOST_PUBLIC_IP>:9000/health
```

Then, through the Worker, with a valid JWT: the same `/query` request should return the
same body.

## 8. Data footprint and refresh

| Artifact | Approx. size |
|---|---|
| `data/search_layer/catalog_golden_records.jsonl` | ~100 MB |
| `data/golden_records/` | < 1 MB today; grows with the manual corpus |
| Service memory after load | ~200 MB |
| Startup load time | ~1.5 s on the development machine |

Refresh: regenerate data on the ingestion machine, copy it to the host, restart the
service. The service reads data only at startup.
