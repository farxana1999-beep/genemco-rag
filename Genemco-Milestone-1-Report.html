Please read — how the catalogue data was sourced

The Shopify Admin API token supplied so far is a placeholder and returns 401 Unauthorized. So that work could continue, the 20 SKUs in this report were read from the public genemco.com product feed instead. That feed carries no real inventory counts, no cost data, and no unpublished products.

Every record sourced this way is stamped sync_mode: "public_storefront" so it can never be mistaken for authoritative data. Supplying a working Admin token replaces it cleanly — no rebuild required.

Note how the manual labels its rows: 85, 101 is a list, 12 - 19 is a range. A compressor sold as an RXF-85 has to know that its oil charge lives in the row marked 85, 101 — 36 gallons — and that the other three rows describe different machines entirely.

One manual, several products

The same document describes both the packaged unit (RXF-85) and the compressor inside it (XJF-151L). A single SKU needs specifications from both tiers, and from neither of the machines it isn't. The system now reads six different labelling conventions found in this one manual:

Why the variant letter matters

XJF 151A, 151M, 151L and 151N are rated at 342, 403, 500 and 598 CFM respectively. Treating them as one model would have quietly averaged four different machines into one product page. The system reads the variant letter from the product title and keeps only the matching row.

Across the whole manual, 116 specification rows were extracted for every machine it covers. 14 of those belong to WHB03 and were kept; the rest were correctly attributed elsewhere.

When two sources disagree, nothing is silently overwritten. The nameplate wins on electrical and serial-number fields; the manual wins on dimensions and performance; and any numeric disagreement beyond 5% is recorded as a conflict for a person to resolve. This run produced zero conflicts — expected, since only one technical source was available. The rule becomes active once nameplate photographs are supplied.

FAQs are generated for SEO, then put through a check that has nothing to do with language: every number in an answer must already exist in that product's verified specifications, or the answer is thrown away.

An answer the system refused to publish

The language model also produced this, and it was discarded automatically:

Rejected — logged to logs/exceptions.jsonl
Q: What is the CFM rating at 3550 RPM for the Frick RXF-85-H?
   rejected: unverified numbers in answer: [3550.0]

The figure 3550 appears in the manual only as part of a column heading — "Cfm 3550 Rpm" — never as a measured value for this machine. The system had no verified source for it, so it refused. Every rejection is written to an audit log with its reason.

One decision for Genemco

This is arguably stricter than needed: 3550 RPM is genuine information from the manual, just held in a heading rather than a value. Loosening the rule to admit qualifiers from column headings is a small change. We recommend leaving it strict, but it is your call.

Each product's answers also come as a FAQPage structured-data block that drops straight into a Shopify product template for search-engine rich results.

05 Safety warnings are quoted, never paraphrased

Specification tables and safety warnings travel separate paths. Warnings are stored word for word with their page number and are returned exactly as printed. They are structurally incapable of reaching the FAQ writer — a language model rewording a DANGER notice is a safety problem, not a quality problem.

The first query is the demanding one. Genemco stocks both an RXF-85-H and an RXF-85H — one hyphen apart, different units. Asked for the first, the system returned only that machine: all twelve top results are WHB03, its product record followed by its individual specifications. The near-twin does not appear at all. Two products whose names differ by a single character are kept apart rather than blurred together.

The second query contains no model number at all, and still returned the correct 500 HP Vilter package from a plain description of it.

The fourth shows the separation clearly: the correct pump scored 8.88 while the next candidate fell to −8.79. The system is not guessing between close options; it either has a match or plainly does not.

09 Known limits, stated plainly

Four things are not finished. None blocks Milestone 1, and all are listed here rather than left to be discovered later.

  1. Two tables were read but not attached to products. Allowable Flange Loads and CH Coupling Data are organised by pipe and coupling size rather than by machine model, so they apply to the whole RXF range at once. We recommend making them searchable reference text rather than forcing them into per-product fields — a short piece of work, pending your preference.
  2. Some fractions in the coupling table are damaged. The manual uses a custom font for fractions that extracts as unreadable characters. Affects that one table.
  3. Shared manuals are stored per product. A manual covering many SKUs is currently duplicated for each. Harmless at 20 SKUs; it needs restructuring before the full catalogue run, and is accounted for in the Milestone 2 plan.
  4. Source-precedence rules are untested against real conflicting data. The logic is covered by automated tests, but has never seen a real nameplate disagree with a real manual. Nameplate photographs would close this.
